# HTML 协作报告：视觉系统、组件结构与执行规则

## 导航

定位与样式§1—3；图片与证据§4—7；模板执行与降级§8—10；维护检查§11；双格式与组件映射§12—13；资源与交付§14—16。

## 1. 定位

HTML 是协作过程的视觉摘要，不是详细文档的网页版。它用于让学生和教师快速看见本轮最重要的成果、判断、AI边界、可复用经验与下一步。详细过程和完整证据仍由文档版承担。

## 2. 视觉系统

- 风格：Swiss International Style，严格网格、扁平设计、清楚的留白与层级。
- 色彩：黑、白、灰为主；只使用一个饱和度高、明度中等的主题色。主题色优先从作品中提取，没有可靠作品图时由模板选择。
- 网格：桌面端12栏；移动端单栏或双栏重排。内容区最大宽度约1180px。
- 字体：中文正文与标题使用 HarmonyOS Sans SC；英文、数字、标签、编号使用 JetBrains Mono。
- 品牌：顶部使用深色品牌条。学校Logo置于左上或右上，与“人工智能素养 I”保持明显间距；Logo颜色需与背景和主题色协调，不得牺牲识别度。
- 形态：避免装饰性阴影和拟物效果，以边线、色块、字号和跨栏关系建立设计感。

## 3. 固定组件结构

1. **项目概览**：项目名称、作品形式、当前状态、一句话概括本轮协作；同时简要呈现已经确认的需求锚点或成功标准。
2. **成果预览（可选）**：展示1—6张学生提供或确认的最终／代表性成果。固定在项目概览之后、核心亮点之前；多图采用纯CSS横向滑动卡片。
3. **核心亮点**：关键发现、可复用经验、下一关任务均为候选组件；无证据、价值低或相互重复时删除或合并。亮点不能只复述过程，应至少提升一个抽象层级，说明这次实践改变了什么判断、形成了什么可迁移机制，以及怎样进入下一次验证。
4. **过程回顾与评估**：初始想法与需求锚定、关键转折、学生判断、AI作用与边界。只记录真正影响方向或结果的过程。
5. **成果与验证**：当前成果、验证结果、待解决问题。严格区分“已经生成”“经过测试”和“仍待确认”。
6. **证据小字**：固定放在底部，说明报告依据与未知边界。

## 4. 图片执行规则

- 展示1—6张学生提供或确认的最终成果或代表性成果；优先选择能够共同说明最终交付范围的图片，不收录一般过程截图。
- 图片位置固定在“项目概览”之后、“核心亮点”之前，作为整页主视觉区域。
- 不得由Coach自行生成、替换或推测成果图。
- 没有可靠图片时，删除整个图片组件，或给 `.preview-wrap` 添加 `hidden` 属性；标题、数量、滑动提示和上下间距必须一起消失，不显示空框、默认图或占位符。后续“核心亮点”自然上移。
- 多图使用CSS `overflow-x: auto` 与 `scroll-snap`，不依赖JavaScript；桌面端悬停效果只是增强，不能成为查看内容的必要操作。
- 每张图只写简短名称和序号；图片较多时注意单文件体积，必要时转为合理尺寸的WebP。

## 5. 内容与证据规则

- 先写最重要的核心亮点，再补充必要过程；重点内容可以展开，次要内容简写。
- 有事实、有价值才写；无证据的部分直接省略，不为填满版面制造转折、验证或成长叙事。
- 学生在其他模型、平台或对话窗口执行时，只能依据学生带回的截图、文件、错误信息与个人说明继续分析。
- 明确区分：当前窗口直接发生的内容、学生转述的外部执行、无法确认的未知过程。
- 不把作品生成等同于掌握能力；不评分，不推断人格、动机、原创性或学习增益。
- “关键发现”回答认知或判断发生了什么变化；“可复用经验”回答以后具体怎样做及其适用条件。两者重复时合并。
- “下一关任务”应是现实、可执行的小挑战，不是机械布置作业。
- “学生判断”记录有依据的取舍、保留、修改或拒绝；不要求正式列出两条备选。只知道修改要求、不知道理由时不能补造理由，没有可确认判断则删去对应项。
- “AI作用与边界”既写有效贡献，也检查AI是否误判、遗漏关键卡点、重复推进、未遵守约束或产生失败结果。没有证据时不虚构失误，但不能只写正面作用。

## 6. 报告前置询问

- 报告访谈以reflection-report.md为准，按缺失信息灵活开放追问，不固定总轮数。状态已有记录不重问；姓名需要且未知时自然询问，多名成员按确认顺序填写，不愿提供可省略。
- 如果学生在其他模型或平台完成作品，但当前对话中没有可用成果，Coach可在报告前一次性询问其是否愿意提供最终成品、代表性截图或可访问链接，用于报告展示与成果验证。这是补充证据，不是生成报告的门槛。
- 任务已经中断、暂时没有成果图、链接无法访问或学生不愿提供时，照常生成阶段报告；不反复索要，也不根据描述自行补画或推测成果。可自然询问：“如果作品是在其他平台完成的，可以把最终成品、代表性截图或链接发给我，我会用于报告展示和验证；如果暂时没有或任务已中断，也不影响生成阶段报告。”
- 英文标签 `Group Member：` 使用 JetBrains Mono，成员姓名使用 HarmonyOS Sans SC。
- 如果学生不愿提供姓名，删除成员行，不显示占位符。

## 7. 自适应规则

- 项目概览与底部证据说明固定保留。
- 其余组件是候选，不要求全部出现，也不要求平均分配篇幅。
- 完成型项目：突出成果、验证与可复用经验。
- 迭代型项目：突出关键转折、学生判断与技术验证。
- 暂停／中断型项目：明确当前状态，突出已验证内容、停止原因和重启条件，不包装成成功案例。
- 简单任务没有明显转折时，删除“关键转折”；AI没有直接参与外部执行时，重点说明信息边界。

## 8. 高还原执行规则

- 还原效果依赖“复用固定HTML/CSS”，而不是让另一个AI根据文字描述重新设计页面。
- Skill应将模板作为只读资产调用：AI只填充数据槽、替换主题色变量、插入已确认的Logo与1—6张成果图，并删除不适用的可选组件。
- 不允许AI擅自改变12栏网格、最大内容宽度、断点、字体栈、品牌条、模块顺序和基础间距体系。
- 主题色只修改CSS变量 `--accent`；黑、白、灰及分隔线色保持固定，除非可读性检查不通过。
- Logo、字体和图片优先以内嵌资源输出；Logo与课程名之间保持既定间距，不能压缩到难以识别。
- 核心亮点固定使用纵向色块组件，与后续网格化的过程、成果模块形成层级区分；内容变长时纵向增长，不改成并列表格。
- 内容写入后检查：标题是否溢出、卡片是否出现空项、移动端是否单栏、图片是否完整显示、打印时是否断裂。
- 如果平台只能输出代码，必须给出完整HTML，不得只给内容数据或重新描述视觉风格。

## 9. 通用生成与降级

- 优先生成单文件HTML：CSS、字体、Logo与预览图尽可能内嵌，避免外部依赖。
- 若平台不能创建文件，则输出完整HTML代码，提示保存为 `.html` 后用浏览器打开。
- 若无法嵌入字体，依次回退到 HarmonyOS Sans SC／PingFang SC／Microsoft YaHei 与 JetBrains Mono／等宽系统字体。
- 若无法取得有效图片地址，删除图片模块；不能因此阻止报告生成。
- 页面须响应式适配手机和电脑，并支持浏览器打印或转PDF。

## 10. 固定证据说明

> 本报告依据当前对话、学生提供的作品及外部执行信息生成；未提供或无法确认的过程不作推测。

## 11. HTML测试标准

HTML测试必须同时覆盖两条线，任何一条不通过都不能视为模板完成。

### A. 视觉与跨模型复现

- 视觉是否符合既定Swiss网格、黑白灰主体系、单主题色、字体、Logo、信息层级和响应式规则。
- 不同通用模型调用同一固定模板时，能否在不重写设计的前提下正确填充内容、替换主题色、插入或删除成果图、删除无证据模块。
- 至少检查桌面端、手机端和浏览器打印；不能出现标题溢出、空卡片、Logo变形、图片裁断、字体错用和移动端横向滚动。
- 跨模型测试的目标是验证“固定资产能否被稳定执行”，不是比较不同模型自由设计网页的能力。

### B. 内容闭环与Coach质量

- 核对需求、关键判断、实际过程、作品状态、验证范围与可迁移经验之间是否有依据的对应。暂停或未完成时展示真实停点与未知，不为形成完整链条补造事件。
- 落脚点必须是学生实际交付的作品、Skill、视频、网页或其他成果，而不是停留在一次聊天过程的摘要。
- Coach应综合完整上下文、学生反馈、作品材料和跨平台证据，利用语义理解识别真正的转折、因果关系、取舍与可迁移机制；不能只摘抄高频句子或机械对应栏目。
- 推理必须受到证据约束：可以从多段对话中归纳隐含逻辑，但不能补写未观察到的操作、测试结果和成长故事。
- 核心亮点应高于操作日志一个层级，既回答“这次为什么重要”，也回答“对作品和以后实践有什么用”。

## 12. 与详细文档版的关系

- 正式流程是：先基于完整对话、学生回顾、外部证据和交付作品生成详细文档版；确认事实与判断后，再从文档版提炼HTML视觉摘要。当前直接由对话生成HTML只用于模板原型测试。
- HTML与详细文档必须使用同一份结构化事实和证据底座，项目状态、关键判断、交付成果和验证结论不得互相矛盾。
- HTML负责快速呈现最重要的结论与证据；文档版在此基础上补充需求演变、备选路线、关键判断依据、完整验证记录、AI失误与修正、作品评估和经验适用条件。
- HTML只能删减、重组和视觉强化文档中已有且确认的内容，不能新增文档版没有依据的结论。
- 文档版不是把HTML卡片逐条扩写，也不是重新生成一份泛泛总结；它是完整报告和事实来源，HTML则是从中提炼的重点展示。
- MD采用四部分：作品与需求、关键过程与证据、人与AI的作用和边界、可带走的方法资产。HTML依照下方映射提炼；信息结构变化不要求重排模板视觉。

## 13. 本Skill中的模板位置与内容对应

固定资产：`../assets/collaboration-report-template.html`。它是本Skill的固定报告母版，不得用作品本身页面替换。参考规范不会自动创建HTML，必须实际读取模板并生成文件。

| 模板组件 | 从MD提取的内容 | 保留与删除 |
|---|---|---|
| 首屏与项目概览 | 名称、形式、状态、需求锚点、一句话协作概括 | 必留；标题按意义断行，不为了三行补词 |
| 成员行 | 已提供的真实成员姓名及顺序 | 未提供则整行删除 |
| 成果画廊 | 1—6张已提供或确认的代表成果 | 无图整组删除；一张不显示滑动提示，多张可横滑 |
| 核心亮点 | 最重要发现、经验、可执行下一步 | 按实际价值删并，不把三个候选当必填 |
| 可复用经验内的方法资产 | 有据的提示词/提问方式、工具路线、避坑方法；场景与适用条件 | 复用纵向色块内的小块，三类有则留、无则删；不凑提示词、不重复正文 |
| 过程回顾 | 需求演变、关键转折、人作出的判断、AI贡献与边界 | 保留有据条目，角色使用实际名称；不能套出虚构学生行为 |
| 成果与验证 | 交付、已验证范围、剩余问题 | 状态与MD一致，未测试就如实说明 |
| 底部证据 | 资料依据与未观察部分 | 必留，可补充本项目具体范围 |

## 14. 模板保护与资源处理

模板文件本身作为只读母版，生成时复制后填充。允许替换文本槽、主题色、已确认资源，增减同类数据条目，删除可选组件；禁止重写CSS或任意改布局。保留原12栏、1180px最大宽、820px与520px断点、字号层级和间距，黑色品牌条及纵向亮点色块。中文使用Harmony，英文数字使用JetBrains Mono。既有短英文标签可保留，报告叙述与解释用中文。

包内字体和校徽资源由原型示范页原有内嵌数据提取，附资源清单。校徽只有本课程及机构已确认适用时使用；不能因模板有图就替别校学生挂上该校标志。没有可用Logo时删除图片，保留品牌条和课程文字并清除空分隔占位。示范报告的学生内容和成果图不属于当前项目素材，不得复制进新报告。

嵌入字体时将实际文件转为data URI，格式按文件类型匹配；不能取得字体则采用规范列明的回退并说明差异。删除无图、无姓名或无内容模块后同步删除标题、提示和空白。槽位是文本时必须HTML转义，不能把用户提供的字符当脚本或HTML执行。方法资产的长提示词使用模板内pre样式换行；标明原文、整理版或待测试建议，不用生成的示例冒充实际提示。

字体文件为既有子集，不保证任意新内容字形齐全。生成后检查覆盖，缺字用明确的系统回退或用户提供的完整同字体，说明差异。数字英文优先JetBrains，中文Harmony；不能承诺设备缺字时一模一样。

打印多图时应确保各图可见；如果原模板的横向画廊导致打印裁断，允许仅添加打印媒体下的必要展开修复，并记录，不能改屏幕版式。长块打印需允许分页，不能为避免分页导致内容被裁切。

## 15. 交付检查

核对MD与HTML的项目状态、数字、贡献归属和验证结论；检查无残余`{{...}}`和`__...__`占位、无示范项目遗留、无断图和空卡。桌面、手机、打印分别检查，记录实际检查范围，未运行不写PASS。可运行`scripts/check_report.py --md 报告.md --html 报告.html`检查基本文件与占位；它不证明语义正确或视觉达标。

## 16. 例外与优先级澄清

- 本文件第11节的跨模型双线测试针对模板维护，不是每个学生报告的必经门槛。暂停或无成果时按实际状态保留需求、已发生过程、已有验证及未知边界，不为“闭环”补写成果。
- 第12节先确认再提炼是默认路线；学生明确要求一次交付两份时服从，同一份可核对事实用于两份，未确认判断明确标注，不冒充学生确认。
- 无图优先直接删除整个图组；若用hidden隐藏，仍须清除所有未替换槽位。
- 没有适用Logo时，允许仅在生成副本对课程文字移除左分隔线及对应内边距，其余CSS保持。该局部必要处理和打印展开修复不属于自由重设计。
